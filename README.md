# depgraph

## Общее описание

depgraph это консольный инструмент визуализации графа зависимостей npm-пакетов. Он получает зависимости напрямую из репозитория npm (например https://registry.npmjs.org), строит полный граф с учетом транзитивных зависимостей и выводит его в одном из трех видов: текстовый список связей, порядок загрузки зависимостей или описание на языке диаграмм Graphviz.

Практическая работа 2, вариант 31, дисциплина "Конфигурационное управление". Реализованы все пять этапов:

1. CLI с настраиваемыми параметрами и обработкой ошибок
2. получение прямых зависимостей npm-пакета заданной версии
3. построение графа зависимостей алгоритмом BFS с рекурсией, обработка циклов, тестовый режим
4. вывод порядка загрузки зависимостей и сравнение с реальным менеджером пакетов
5. представление графа на языке Graphviz и сравнение со штатным инструментом npm

Менеджеры пакетов и сторонние библиотеки для получения зависимостей не используются: только стандартная библиотека Python (urllib, json, re, argparse и другие). Разбор диапазонов версий semver тоже написан с нуля.

## Требования

- Python 3 (проверено на 3.13), внешние библиотеки не нужны
- make для запуска команд из Makefile
- Graphviz (команда dot) нужен только чтобы превратить вывод --graphviz в картинку
- npm нужен только для сравнения результатов, для работы инструмента он не требуется

## Параметры

Все параметры задаются опциями командной строки.

- --package - имя анализируемого пакета (обязательный)
- --repo - URL репозитория или путь к файлу тестового репозитория (обязательный)
- --test-mode - режим работы с тестовым репозиторием, --repo тогда путь к файлу
- --version - версия пакета в формате semver, например 4.3.4 (обязательный)
- --load-order - вместо графа вывести порядок загрузки зависимостей пакета
- --graphviz - вместо графа вывести описание графа на языке Graphviz (DOT)

Опции --load-order и --graphviz взаимоисключающие. Если не указана ни одна из них, выводится текстовый граф.

## Режимы вывода

Текстовый граф (по умолчанию). Для каждого пакета в порядке обхода в ширину выводится строка "пакет -> зависимости", затем число пакетов в графе и список найденных циклов.

    Граф зависимостей debug@4.3.4:
    debug@4.3.4 -> ms@2.1.2
    ms@2.1.2 -> нет
    Всего пакетов: 2
    Циклические зависимости: нет

Порядок загрузки (--load-order). Нумерованный список, в котором каждый пакет стоит после всех своих зависимостей, а анализируемый пакет последний. Ниже в разделе "Порядок загрузки".

Graphviz (--graphviz). Описание графа на языке DOT, которое можно передать программе dot для построения картинки. Ниже в разделе "Визуализация в формате Graphviz".

## Как это работает

### Проверка параметров (config.py)

Перед работой параметры проверяются. При ошибке в stderr выводится сообщение "Ошибка: ..." и программа завершается с кодом 1.

- имя пакета: непустое, не длиннее 214 символов, корректное имя npm (допускаются scope-пакеты вида @babel/core); в тестовом режиме только большие латинские буквы
- репозиторий: в обычном режиме URL со схемой http или https и хостом, без пробельных символов; в тестовом режиме существующий читаемый файл
- версия: формат X.Y.Z, допускаются суффиксы -prerelease и +build
- отсутствие обязательной или неизвестная опция, а также одновременное использование --load-order и --graphviz: ошибка argparse с кодом 2

### Получение данных (npm.py)

Для каждого пакета запрашивается один документ по адресу URL/имя в сокращенном формате (заголовок Accept: application/vnd.npm.install-v1+json). В нем есть все версии пакета с их зависимостями и dist-tags. Документ каждого пакета запрашивается один раз и кэшируется. Из поля dependencies берутся прямые зависимости. Поля devDependencies и peerDependencies не учитываются. Поле optionalDependencies отдельно не читается, но npm при публикации копирует такие зависимости и в dependencies, поэтому они попадают в граф.

Сетевые ошибки превращаются в понятные сообщения: пакет или версия не найдены (HTTP 404), другие ошибки HTTP, репозиторий недоступен, некорректный JSON, неожиданный формат ответа.

### Разрешение версий (semver.py)

Требуемая версия зависимости задается диапазоном (^1.2.0, ~2.0, 1.x, >=1 <3, 1.0.0 || 2.x, 1.2.3 - 2.3.4, *) или dist-tag (latest). Диапазон разрешается в конкретную версию по правилам npm (функция pick_version в npm.py):

1. если спецификация совпадает с именем dist-tag, берется версия этого тега
2. если версия из тега latest подходит под диапазон, берется она, даже если существует более новая подходящая версия
3. иначе берется наибольшая подходящая версия, при этом устаревшие (deprecated) версии берутся, только если других подходящих нет
4. пререлизы выбираются только если стабильных подходящих версий нет

Спецификации, которые не являются версиями (git-адреса, file:, алиасы npm:), не поддерживаются, для них выводится ошибка.

### Построение графа (graph.py)

Узел графа это пара (имя, версия). Граф строится обходом в ширину (BFS) с рекурсией: функция expand_level обрабатывает один уровень, собирает зависимости следующего уровня и вызывает себя для него. Уже обработанные узлы пропускаются, поэтому каждый пакет запрашивается один раз.

Циклические зависимости (в том числе пакет, зависящий от самого себя) не приводят к бесконечному обходу, потому что повторно посещенный узел не обрабатывается. После построения граф проверяется на циклы функцией find_cycles, найденные циклы выводятся отдельно, каждый цикл один раз.

### Порядок загрузки (loadorder.py)

Порядок строится обходом в глубину без рекурсии (явный стек) по уже построенному графу. Пакет записывается в результат, когда обработаны все его зависимости (обратный порядок обхода). Поэтому каждый пакет стоит после всех своих зависимостей, а анализируемый пакет последний. Зависимости одного пакета обходятся в том порядке, в котором они перечислены в репозитории, поэтому результат детерминирован. Каждый пакет встречается один раз.

Циклические зависимости не имеют корректного порядка загрузки: два пакета в цикле не могут оба стоять после друг друга. Поэтому ребро, замыкающее цикл (ведущее в пакет, который еще обрабатывается), разрывается. Такие ребра выводятся в конце в разделе "Разорванные циклические связи".

    Порядок загрузки зависимостей A:
    1. D
    2. C
    3. B
    4. A
    Разорванные циклические связи:
      C -> A

### Визуализация в формате Graphviz (dot.py)

Опция --graphviz выводит граф на языке DOT и больше ничего, поэтому вывод можно сразу передать программе dot. Структура вывода:

- заголовок digraph с именем анализируемого пакета
- общий стиль узлов (прямоугольники)
- объявление каждого узла один раз, корневой пакет выделен голубым цветом (так видны и пакеты без зависимостей)
- по одной строке на каждое ребро "зависимый -> зависимость"

Все имена берутся в кавычки, внутри кавычек экранируются двойные кавычки и обратная косая черта. Циклические связи выводятся как обычные ребра, на картинке это стрелки назад.

Чтобы получить картинку, нужен Graphviz (в Codespace: sudo apt-get update && sudo apt-get install -y graphviz):

    make run ARGS="--package chalk --repo https://registry.npmjs.org --version 4.1.2 --graphviz" | dot -Tpng -o chalk.png

Файлы изображений в репозиторий не добавляются (они перечислены в .gitignore).

### Тестовый режим

Вместо URL в --repo передается путь к текстовому файлу, в котором каждая строка описывает пакет: имя большими латинскими буквами, двоеточие и список его прямых зависимостей через пробел. Пустые строки игнорируются. Версии в тестовом режиме не используются, но параметр --version остается обязательным.

    A: B C
    B: D
    C: D
    D:

## Сборка, запуск и тесты

Сборка не требуется. Команды из корня репозитория:

    make run ARGS="--package debug --repo https://registry.npmjs.org --version 4.3.4"
    make run ARGS="--package debug --repo https://registry.npmjs.org --version 4.3.4 --load-order"
    make run ARGS="--package debug --repo https://registry.npmjs.org --version 4.3.4 --graphviz"
    make test
    make clean

- make run запускает программу, параметры передаются через ARGS
- make test запускает все тесты (unittest)
- make clean удаляет каталоги `__pycache__`

Тесты не обращаются к сети: для проверки работы с репозиторием поднимается локальный HTTP-сервер, имитирующий репозиторий npm. Тесты покрывают проверку параметров, разбор диапазонов версий, выбор версии, построение графа, циклы, порядок загрузки, вывод DOT и CLI целиком.

## Структура репозитория

- src/depgraph - исходный код
- tests - тесты (test_*.py), поддельный репозиторий npm (fake_registry.py)
- tests/data - файлы тестовых репозиториев: repo.txt (ромб), order.txt (граф из семи пакетов с общими зависимостями), cycle.txt (цикл A, B, C), selfloop.txt (пакет зависит от себя)
- Makefile - команды run, test, clean
- .gitignore - служебные файлы Python и редакторов, изображения, архивы

## Сравнение с npm

Все сравнения сделаны с npm 10.9.9 по состоянию репозитория на 1 ноября 2026 года. Результаты зависят от времени, так как новые версии пакетов публикуются постоянно.

### Порядок загрузки (этап 4)

У npm нет команды, которая выводит порядок загрузки: пакеты устанавливаются параллельно, а порядок вывода npm ls алфавитный. Поэтому сравнение сделано двумя способами.

Первый способ: сравнение состава дерева. Для пакета выполнялась команда npm install имя@версия --package-lock-only --ignore-scripts, которая строит полное дерево зависимостей без скачивания пакетов, и набор пар (имя, версия) из package-lock.json сравнивался с набором пакетов из нашего графа.

| Пакет | Пакетов у depgraph | Пакетов у npm | Расхождение |
| --- | --- | --- | --- |
| debug@4.3.4 | 2 | 2 | нет |
| chalk@4.1.2 | 6 | 6 | нет |
| yargs@17.7.2 | 16 | 16 | нет |
| @babel/core@7.22.0 | 39 | 39 | нет |
| express@4.18.2 | 68 | 68 | нет |
| eslint@8.57.0 | 99 | 99 | нет |
| webpack@5.88.0 | 82 | 82 | нет |
| jest@29.7.0 | 266 | 266 | нет |
| mocha@10.2.0 | 79 | 78 | лишний yargs-parser@20.2.9 |
| request@2.88.2 | 48 | 47 | лишний extsprintf@1.4.1 |

Второй способ: сравнение с реальным порядком загрузки в Node.js. Пакет express@4.18.2 был установлен командой npm install, затем в Node.js перехвачен Module.prototype.load и записан порядок, в котором завершилась загрузка главного модуля каждого пакета при выполнении require("express"). Результат: в обоих случаях загружены те же 68 пакетов. В нашем порядке ни одна из 125 зависимостей не нарушена (зависимость всегда раньше зависимого пакета), в реальном порядке нарушено 11 из 125. Точный порядок не совпал.

Причины расхождений:

1. Дедупликация npm. npm старается использовать одну версию пакета для нескольких зависимых, если она подходит им всем, а мы разрешаем каждый диапазон независимо. В mocha@10.2.0 сам mocha требует yargs-parser ровно 20.2.4, а yargs@16.2.0 требует ^20.2.2. Версия 20.2.4 подходит под оба требования, и npm ставит одну копию, а мы выбираем для yargs максимальную подходящую 20.2.9 и получаем две версии. Аналогично в request@2.88.2: jsprim требует extsprintf 1.3.0, а verror требует ^1.2.0, npm использует 1.3.0 для обоих, мы берем для verror версию 1.4.1.
2. Правила выбора версии. Для get-intrinsic тег latest указывает на 1.3.0, хотя опубликована и 1.3.1. npm выбирает версию из latest, если она подходит под диапазон. Выбор по этому правилу реализован в pick_version, после чего расхождение для express исчезло (до этого у нас было 71 пакет против 68 у npm).
3. Условия установки, которые мы не учитываем. npm пропускает версии, не подходящие по engines к текущей версии Node.js, и необязательные зависимости, которые не подходят платформе (os, cpu). Кроме того, npm 7 и новее автоматически устанавливает peerDependencies, а мы их не читаем.
4. Реальный порядок загрузки в Node.js определяется не package.json, а вызовами require в коде пакета. Если пакет подключает зависимость лениво (внутри функции или при первом обращении к свойству), она загружается позже самого пакета. Например, body-parser подключает парсеры при первом обращении, поэтому его главный модуль завершился раньше зависимостей qs, bytes, debug, unpipe и других. Кроме того, порядок одноуровневых зависимостей в Node.js следует порядку вызовов require в исходниках, а у нас порядку в package.json. Поэтому наш порядок это безопасный порядок установки, который гарантирует, что при загрузке пакета все его зависимости уже есть, а не точная запись того, что делает Node.js.

### Визуализация (этап 5)

У npm нет штатного вывода графа в виде диаграммы (в том числе в формате Graphviz). Ближайший штатный инструмент визуализации это команда npm ls --all, которая печатает дерево установленных зависимостей. Для сравнения пакет устанавливался командой npm install имя@версия --ignore-scripts, затем из вывода npm ls --all --json собирался набор ребер "пакет@версия -> зависимость@версия" и сравнивался с набором ребер из вывода --graphviz.

Для chalk@4.1.2 npm ls --all печатает:

    probe@1.0.0
    └─┬ chalk@4.1.2
      ├─┬ ansi-styles@4.3.0
      │ └─┬ color-convert@2.0.1
      │   └── color-name@1.1.4
      └─┬ supports-color@7.2.0
        └── has-flag@4.0.0

Наш граф для того же пакета содержит те же 5 ребер, см. раздел "Примеры использования".

| Пакет | Ребер у depgraph | Ребер у npm ls | Расхождение |
| --- | --- | --- | --- |
| chalk@4.1.2 | 5 | 5 | нет |
| debug@4.3.4 | 1 | 1 | нет |
| yargs@17.7.2 | 19 | 19 | нет |
| express@4.18.2 | 125 | 125 | нет |
| mocha@10.2.0 | 90 | 90 | два ребра различаются |
| webpack@5.88.0 | 117 | 123 | шесть ребер есть только у npm |

Причины расхождений:

1. Peer-зависимости (webpack). npm ls показывает и peerDependencies, потому что npm 7 и новее устанавливает их автоматически. Шесть ребер есть только у npm: schema-utils и terser-webpack-plugin зависят от webpack, ajv-keywords от ajv (две версии), acorn-import-assertions от acorn, update-browserslist-db от browserslist. Мы читаем только dependencies и этих ребер не строим.
2. Дедупликация (mocha). Ребро yargs@16.2.0 -> yargs-parser у нас ведет на версию 20.2.9, а у npm на 20.2.4, потому что npm использует уже установленную для mocha версию, подходящую под диапазон. Причина такая же, как в разделе про порядок загрузки.
3. Необязательные зависимости (mocha). Ребро chokidar@3.5.3 -> fsevents у нас ведет на fsevents@2.3.3, а npm ls показывает fsevents без версии. fsevents нужен только на macOS, на Linux npm его не устанавливает, а мы берем зависимость из поля dependencies, куда npm копирует необязательные зависимости, и показываем ее как обычный пакет.
4. Различие в представлении. npm ls печатает дерево, в котором пакет, нужный нескольким зависимым, повторяется в каждом месте (npm помечает такие повторы как deduped), а список идет в алфавитном порядке. Граф Graphviz показывает каждый пакет один раз, а общие зависимости (например string-width и strip-ansi для yargs) получают несколько входящих стрелок. Поэтому на картинке узлов меньше, чем строк в выводе npm ls, а число ребер совпадает.
5. npm ls описывает дерево, установленное для текущей платформы и версии Node.js, а depgraph описывает зависимости, объявленные в репозитории.

## Примеры использования

## Ограничения

- не читаются peerDependencies, а также devDependencies
- не поддерживаются зависимости-ссылки (git, file:, алиасы npm:)
- не учитываются ограничения engines, os и cpu
- каждый диапазон версий разрешается независимо, без дедупликации как в npm
- для очень глубоких графов обход в ширину ограничен глубиной рекурсии Python, при превышении выводится ошибка
