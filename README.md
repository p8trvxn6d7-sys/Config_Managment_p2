# depgraph

Инструмент визуализации графа зависимостей npm-пакетов. Зависимости получаются напрямую из репозитория, без менеджеров пакетов и сторонних библиотек (только стандартная библиотека Python).

Практическая работа 2, вариант 31. Реализованы этапы 1-4: CLI с проверкой параметров, получение зависимостей пакета заданной версии, построение полного графа зависимостей с учетом транзитивности и вывод порядка загрузки зависимостей.

## Параметры

Все параметры задаются опциями командной строки.

- --package - имя анализируемого пакета (обязательный)
- --repo - URL репозитория или путь к файлу тестового репозитория (обязательный)
- --test-mode - режим работы с тестовым репозиторием, --repo тогда путь к файлу
- --version - версия пакета в формате semver, например 4.3.4 (обязательный)
- --load-order - вместо графа вывести порядок загрузки зависимостей пакета

## Как работает

В обычном режиме для каждого пакета программа запрашивает у репозитория npm документ пакета по адресу URL/имя (например https://registry.npmjs.org/debug) в сокращенном формате. В документе есть список версий с их зависимостями и dist-tags. Из поля dependencies берутся прямые зависимости, поля devDependencies и peerDependencies не учитываются. Поле optionalDependencies отдельно не читается, но npm при публикации копирует такие зависимости и в dependencies, поэтому они попадают в граф.

Требуемая версия зависимости задается диапазоном (^1.2.0, ~2.0, 1.x, >=1 <3, 1.0.0 || 2.x, 1.2.3 - 2.3.4, *) или dist-tag (latest). Диапазон разрешается в конкретную версию по правилам npm (модуль semver.py и функция pick_version в npm.py):

1. если спецификация совпадает с именем dist-tag, берется версия этого тега
2. если версия из тега latest подходит под диапазон, берется она, даже если существует более новая подходящая версия
3. иначе берется наибольшая подходящая версия, при этом устаревшие (deprecated) версии берутся, только если других подходящих нет
4. пререлизы выбираются только если стабильных подходящих версий нет

Спецификации, которые не являются версиями (git-адреса, file:, алиасы npm:) не поддерживаются, для них выводится ошибка.

Узел графа это пара (имя, версия). Граф строится обходом в ширину (BFS) с рекурсией: функция обрабатывает один уровень, собирает зависимости следующего уровня и вызывает себя для него. Уже обработанные узлы пропускаются, поэтому каждый пакет запрашивается один раз, а циклические зависимости (в том числе пакет, зависящий от самого себя) не приводят к бесконечному обходу. После построения граф проверяется на циклы, и найденные циклы выводятся отдельно.

В тестовом режиме читается текстовый файл, в котором каждая строка описывает пакет: имя большими латинскими буквами, двоеточие и список его прямых зависимостей через пробел. Пустые строки игнорируются. Версии в тестовом режиме не используются.

    A: B C
    B: D
    C: D
    D:

## Вывод графа

По умолчанию для каждого пакета в порядке обхода в ширину выводится строка "пакет -> зависимости", затем число пакетов в графе и список циклов.

    Граф зависимостей debug@4.3.4:
    debug@4.3.4 -> ms@2.1.2
    ms@2.1.2 -> нет
    Всего пакетов: 2
    Циклические зависимости: нет

## Порядок загрузки (этап 4)

Опция --load-order выводит порядок загрузки зависимостей заданного пакета. Это такой порядок, в котором каждый пакет стоит после всех своих зависимостей, а сам анализируемый пакет идет последним. Порядок строится обходом в глубину без рекурсии (явный стек) по уже построенному графу и записывает пакет в результат, когда обработаны все его зависимости (обратный порядок обхода). Зависимости одного пакета обходятся в том порядке, в котором они перечислены в репозитории, поэтому результат детерминирован. Каждый пакет в списке встречается один раз.

Циклические зависимости не имеют корректного порядка загрузки: два пакета в цикле не могут оба стоять после друг друга. Поэтому ребро, замыкающее цикл (ведущее в пакет, который еще обрабатывается), разрывается. Такие ребра выводятся в конце в разделе "Разорванные циклические связи".

    Порядок загрузки зависимостей A:
    1. D
    2. C
    3. B
    4. A
    Разорванные циклические связи:
      C -> A

### Сравнение с npm

Сравнение сделано для версии npm 10.9.9 по состоянию репозитория на 1 ноября 2026 года. Результаты зависят от времени, так как новые версии пакетов публикуются постоянно.

У npm нет команды, которая выводит порядок загрузки: пакеты устанавливаются параллельно, а порядок вывода npm ls алфавитный. Поэтому сравнение сделано двумя способами.

Первый способ: сравнение состава дерева. Для пакета выполнялась команда npm install имя@версия --package-lock-only --ignore-scripts, которая строит полное дерево зависимостей без скачивания пакетов, и набор пар (имя, версия) из package-lock.json сравнивался с набором пакетов из нашего графа.

| Пакет | Пакетов у depgraph | Пакетов у npm | Расхождение |
| --- | --- | --- | --- |
| debug@4.3.4 | 2 | 2 | нет |
| chalk@4.1.2 | 6 | 6 | нет |
| yargs@17.7.2 | 16 | 16 | нет |
| @babel/core@7.22.0 | 39 | 39 | нет |
| express@4.18.2 | 68 | 68 | нет |
| eslint@8.57.0 | 99 | 99 | нет |
| webpack@5.88.0 | 82 | 82 | нет |
| jest@29.7.0 | 266 | 266 | нет |
| mocha@10.2.0 | 79 | 78 | лишний yargs-parser@20.2.9 |
| request@2.88.2 | 48 | 47 | лишний extsprintf@1.4.1 |

Второй способ: сравнение с реальным порядком загрузки в Node.js. Пакет express@4.18.2 был установлен командой npm install, затем в Node.js перехвачен Module.prototype.load и записан порядок, в котором завершилась загрузка главного модуля каждого пакета при выполнении require("express"). Результат: в обоих случаях загружены те же 68 пакетов. В нашем порядке ни одна из 125 зависимостей не нарушена (зависимость всегда раньше зависимого пакета), в реальном порядке нарушено 11 из 125. Точный порядок не совпал.

Причины расхождений:

1. Дедупликация npm. npm старается использовать одну версию пакета для нескольких зависимых, если она подходит им всем, а мы разрешаем каждый диапазон независимо. В mocha@10.2.0 сам mocha требует yargs-parser ровно 20.2.4, а yargs@16.2.0 требует ^20.2.2. Версия 20.2.4 подходит под оба требования, и npm ставит одну копию, а мы выбираем для yargs максимальную подходящую 20.2.9 и получаем две версии. Аналогично в request@2.88.2: jsprim требует extsprintf 1.3.0, а verror требует ^1.2.0, npm использует 1.3.0 для обоих, мы берем для verror версию 1.4.1.
2. Правила выбора версии. Для get-intrinsic тег latest указывает на 1.3.0, хотя опубликована и 1.3.1. npm выбирает версию из latest, если она подходит под диапазон. Выбор по этому правилу реализован в pick_version, после чего расхождение для express исчезло (до этого у нас было 71 пакет против 68 у npm).
3. Условия установки, которые мы не учитываем. npm пропускает версии, не подходящие по engines к текущей версии Node.js, и необязательные зависимости, которые не подходят платформе (os, cpu). Кроме того, npm 7 и новее автоматически устанавливает peerDependencies, а мы их не читаем. В проверенных пакетах такие различия не встретились, но в других пакетах возможны.
4. Реальный порядок загрузки в Node.js определяется не package.json, а вызовами require в коде пакета. Если пакет подключает зависимость лениво (внутри функции или при первом обращении к свойству), она загружается позже самого пакета. Например, body-parser подключает парсеры при первом обращении, поэтому его главный модуль завершился раньше зависимостей qs, bytes, debug, unpipe и других. Кроме того, порядок одноуровневых зависимостей в Node.js следует порядку вызовов require в исходниках, а у нас порядку в package.json. Поэтому наш порядок это безопасный порядок установки, который гарантирует, что при загрузке пакета все его зависимости уже есть, а не точная запись того, что делает Node.js.

## Проверки и ошибки

При ошибке в stderr выводится сообщение вида "Ошибка: ..." и программа завершается с кодом 1.

- имя пакета: непустое, не длиннее 214 символов, корректное имя npm; в тестовом режиме только большие латинские буквы
- репозиторий: в обычном режиме URL со схемой http или https и хостом; в тестовом режиме существующий читаемый файл
- версия: формат X.Y.Z, допускаются суффиксы -prerelease и +build
- пакет не найден в репозитории (HTTP 404), другие ошибки HTTP, недоступный репозиторий, некорректный JSON, неожиданный формат ответа
- версия пакета отсутствует в репозитории, ни одна версия не подходит под диапазон, неподдерживаемая спецификация версии
- тестовый репозиторий: неверный формат строки, пакет отсутствует в файле
- слишком глубокий граф (превышена глубина рекурсии Python)
- отсутствие обязательной или неизвестная опция: ошибка argparse с кодом 2

## Запуск

    make run ARGS="--package debug --repo https://registry.npmjs.org --version 4.3.4"
    make run ARGS="--package debug --repo https://registry.npmjs.org --version 4.3.4 --load-order"

## Тесты

    make test

Тесты не обращаются к сети: для проверки работы с репозиторием поднимается локальный HTTP-сервер, имитирующий репозиторий npm. Файлы тестовых репозиториев лежат в tests/data:

- repo.txt - ромб: A зависит от B и C, оба зависят от D
- order.txt - граф из семи пакетов с общими зависимостями E и G
- cycle.txt - цикл A, B, C
- selfloop.txt - пакет зависит от себя
